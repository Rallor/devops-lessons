# Етап 5. Перший інцидент → production readiness (тижні 21–23)

## Тригер
У пʼятницю ввечері застосунок 40 хвилин віддавав помилки на половину запитів. Команда дізналася про це з листа клієнта в понеділок. Метрики показували «CPU в нормі».

## Вимоги етапу
1. SLI і SLO для ключових сценаріїв погоджені й записані.
2. Error budget policy: що відбувається з релізами, коли бюджет вичерпано.
3. Алерти на симптоми (burn rate), кожен із runbook і власником; жодного алерту без дії.
4. Логи централізовані, retention і вартість відомі; кореляція через `trace_id`.
5. Load test визначив межу потужності й вузьке місце.
6. DR-вправа: RPO і RTO заміряні, а не задекларовані.
7. Severity levels і процес інциденту; перший інцидент закритий blameless postmortem.
8. AI-функція продукту має власні SLI: латентність, помилки провайдера, вартість токенів.
9. AI-агент для triage, якщо використовується, працює read-only і його дії логуються.
10. Пройдено PRR-чекліст.

## ADR етапу
- **ADR-016.** Збір метрик на PaaS: pull-модель погано лягає на інстанси за балансувальником. OTel SDK або OBI → Alloy чи OTel Collector → Prometheus проти Application Insights проти Managed Prometheus.
- **ADR-017.** Логи: Loki, ELK чи Log Analytics — вартість ingestion, мова запитів, lock-in.
- **ADR-018.** Цільові SLO і вікно вимірювання; чому не 99.99%.

Штучна деградація ловиться алертом раніше, ніж ти сам її помітиш; від алерту до конкретного запиту — три кліки; DR-вправа з заміряними RPO/RTO; game day закритий постмортемом.
