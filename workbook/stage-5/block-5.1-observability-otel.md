# Блок 5.1 — Основи спостережуваності й OpenTelemetry

**Час:** ~5 год · **Передумови:** Етап 4

## Навіщо це зараз
У тебе є метрики інфраструктури і немає відповіді на питання «чи добре зараз користувачам». Це різні речі, і саме друга закриває тригер етапу.

## Теорія
- Метрики, логи, трейси: на яке питання відповідає кожен сигнал; RED для сервісів, USE для ресурсів.
- OpenTelemetry: SDK, авто-інструментація, Collector, OTLP.
- Trace context між API і воркером через чергу.
- Кардинальність міток: як один `user_id` кладе сховище метрик.
- OBI (eBPF-інструментація) як варіант там, де SDK не додати; ловить і виклики БД, і виклики LLM.

## Завдання
1. Підключи OTel SDK до API і воркера; експортуй метрики й трейси через OTLP.
2. Проведи trace context через чергу: один запит користувача має давати звʼязаний трейс API → черга → воркер.
3. Додай `trace_id` у структуровані логи з Етапу 2.
4. Виміряй RED для головного ендпоінта: rate, errors, duration.
5. Свідомо створи метрику з високою кардинальністю, подивись на наслідки, прибери і опиши в нотатках.
6. Спробуй OBI на одному сервісі без зміни коду; порівняй, що він дає і чого не дає порівняно з SDK.
7. Опиши в `docs/notes/telemetry.md`, які три питання ти тепер можеш відповісти за 30 секунд, а які ще ні.

## Критерії прийому
- [ ] Трейс проходить через чергу цілим
- [ ] Логи містять `trace_id` і корелюються з трейсом
- [ ] RED-метрики збираються для ключових ендпоінтів
- [ ] Експеримент із кардинальністю задокументований

## Пастки
- Авто-інструментація дає трейси, але без бізнес-контексту: імена операцій треба доводити руками.
- Пропагація контексту через чергу не працює сама — потрібно класти заголовки в повідомлення.
- Семплінг, увімкнений наосліп, ховає саме ті рідкісні помилки, заради яких усе будувалось.
