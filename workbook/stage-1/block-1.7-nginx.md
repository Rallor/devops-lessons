# Блок 1.7 — Nginx як reverse proxy

**Час:** ~5 год · **Verify:** `verify/stage-1/80-nginx.sh` · **Передумови:** 1.2, 1.5

## Навіщо це зараз
Два інстанси застосунку існують саме для того, щоб рестарт одного не бачив користувач. Без proxy перед ними це просто два процеси.

## Теорія
- Forward proxy проти reverse proxy: напрямок і мета.
- `server`, `location`, `listen`; порядок матчингу location.
- `proxy_pass`, `proxy_set_header` Host, X-Real-IP, X-Forwarded-For.
- `upstream`, `max_fails`, `fail_timeout` — пасивні health checks у відкритій версії.
- TLS termination, редирект HTTP → HTTPS, HSTS.
- Статика, gzip, `proxy_cache` і `Cache-Control`; коли кешувати небезпечно.
- Логи: формат, `$upstream_response_time`, `$upstream_addr` для дебагу.

## Завдання
1. Опиши `upstream` із двох інстансів (8001, 8002) з `max_fails=2 fail_timeout=10s`.
2. Проксіюй `/` на upstream, статику віддавай напряму з диска.
3. Передай бекенду реальний IP клієнта і перевір, що застосунок його бачить у логах.
4. Увімкни gzip для текстових типів, перевір `curl -H 'Accept-Encoding: gzip' -I`.
5. Налаштуй кеш для статики з довгим строком і для API — без кешу; поясни в нотатках, чому саме так.
6. Додай у формат логу `$upstream_addr` і `$upstream_response_time`; зроби так, щоб було видно, який інстанс відповідав.
7. Зупини один інстанс і покажи логом, що трафік пішов на другий, а користувач не отримав помилки.
8. Зроби `reload` під навантаженням і переконайся, що відповіді не переривались.

## Критерії прийому
- [ ] `verify/stage-1/80-nginx.sh` зелений (включно з рестартом під curl-циклом)
- [ ] `nginx -t` чистий; конфіг у git, а не тільки на сервері
- [ ] У логах видно бекенд і час його відповіді
- [ ] Зупинка одного інстансу не дає користувачу 5xx

## Пастки
- `proxy_pass` зі слешем і без слеша на кінці дають різний шлях бекенду.
- Без `proxy_set_header Host $host` застосунок генерує посилання на внутрішнє імʼя.
- `location /api` і `location /api/` — різні речі; помилка матчингу дає 404 там, де мав бути проксі.
- Кеш на відповіді з `Set-Cookie` віддасть чужу сесію іншому користувачу.
- `restart` замість `reload` рве активні зʼєднання.

## Підказки
<details><summary>Підказка 1</summary>
Перевір, чи проблема в nginx чи в застосунку: `curl -I localhost:8001` напряму з сервера. Якщо бекенд відповідає, а через проксі 502 — дивись error log nginx.
</details>
<details><summary>Підказка 2</summary>
Для перевірки «без 502 під рестартом» запускай curl-цикл із сусідньої машини, а не з того ж сервера: локально ти не побачиш проблем з мережею.
</details>
