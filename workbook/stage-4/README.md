# Етап 4. Хмара як код (тижні 16–20)

## Тригер
Одна VM не тримає доступності: за місяць два простої через обслуговування хоста. Аудитор питає, хто і коли відкрив порт 5432 — відповіді немає, бо все робилось руками в порталі.

## Принцип етапу
Azure і Terraform вивчаються одночасно. Ресурс спершу розбирається концептуально, потім одразу описується кодом. Етапу «наклацати в порталі, потім переписати» немає.

## Вимоги етапу
1. Уся інфраструктура в коді; люди мають Reader у prod; дрейф ловиться щоденним `plan`.
2. `plan` публікується в PR; `apply` у prod лише з пайплайну після approval.
3. Remote state з блокуванням, окремий на середовище, доступ обмежений.
4. Паролі й токени не потрапляють у state і plan.
5. CI автентифікується через OIDC; жодного client secret у GitHub.
6. Ні в кого з людей немає Owner на subscription.
7. Мережа private-by-default; вихідний трафік явний через NAT Gateway.
8. Managed PostgreSQL із PITR і зафіксованим retention.
9. Секрети в Key Vault; доступ через managed identity.
10. Теги на кожному ресурсі, бюджет з алертом створений до першого ресурсу.
11. dev знищується і відтворюється з коду.

## ADR етапу
- **ADR-012.** Compute: VMSS + Ansible, App Service for Containers чи Container Apps; де доречний serverless.
- **ADR-013.** Terraform проти OpenTofu проти Bicep; організація state і модулів.
- **ADR-014.** Managed PostgreSQL проти БД на VM.
- **ADR-015.** Мережева схема і адресний простір із запасом на Етап 6.

Кожен ADR цього етапу містить AWS-відповідник.

## Ворота етапу
`destroy` + `apply` для dev без ручних кроків; ручна зміна в порталі ловиться drift-check; `state pull | grep` не знаходить пароля; PITR-відновлення виконано; бюджет-алерт спрацював.
