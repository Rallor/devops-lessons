# Блок 4.3 — Модулі, середовища, IaC у CI

**Час:** ~6 год · **Передумови:** 4.2

## Навіщо це зараз
Три середовища без модулів перетворюються на три копії коду, які розходяться протягом місяця.

## Теорія
- Власний модуль: `variables` з `validation`, `outputs`, передача даних між модулями.
- Registry і Azure Verified Modules проти власних: коли брати чуже.
- `terraform.tfvars`, `TF_VAR_*`; розділення dev/staging/prod.
- Пайплайн: `plan` коментарем у PR, `apply` з approval, OIDC до Azure, `concurrency` для серіалізації, щоденний drift-check.

## Завдання
1. Винеси мережу, БД, compute й ідентичності в окремі модулі з явними входами і виходами.
2. Додай `validation` на критичні змінні (розмір, регіон, CIDR).
3. Зроби окремі конфігурації середовищ із власним state; переконайся, що dev і prod не перетинаються.
4. Налаштуй OIDC між GitHub і Azure; прибери всі client secret.
5. Побудуй пайплайн: `fmt` і `validate` на PR, `plan` коментарем, `apply` після approval.
6. Додай щоденний drift-check, який створює issue при знайденій різниці.
7. Знищ dev повністю і підніми заново; заміряй час і запиши.

## Критерії прийому
- [ ] Модулі з валідацією; середовища з окремим state
- [ ] У GitHub немає жодного Azure client secret
- [ ] `plan` видно в PR до `apply`
- [ ] Drift-check працює і створює issue
- [ ] `destroy` + `apply` для dev пройдені, час записаний

## Пастки
- Модуль, що приймає 40 змінних, — це не модуль, а копія коду з зайвим шаром.
- `apply` без `concurrency` у CI дає паралельні запуски й конфлікти блокувань.
- OIDC без обмеження на гілку й репозиторій дозволяє чужому workflow отримати токен.
