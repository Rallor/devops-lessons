# Блок 4.2 — State

**Час:** ~4 год · **Передумови:** 4.1

## Навіщо це зараз
State — це джерело правди Terraform і водночас файл із паролями відкритим текстом, якщо ти нічого не зробиш.

## Теорія
- Що таке `.tfstate` і що буде, якщо його втратити.
- Remote state в Storage Account, блокування через blob lease; bootstrap-проблема.
- `state list`, `show`, `mv`, блоки `moved` та `import`; чому ручне редагування небезпечне.
- Секрети в state: `sensitive` ховає лише вивід. Ephemeral-ресурси і write-only аргументи; шифрування state в OpenTofu.
- Розділення state на середовища і межі вибуху.

## Завдання
1. Створи Storage Account під state вручну або окремим bootstrap-конфігом; поясни в нотатках, чому цю курку-яйце вирішують саме так.
2. Перенеси локальний state у remote; переконайся, що блокування працює (запусти два `apply` одночасно).
3. Обмеж доступ до контейнера зі state; перевір, що зайвий principal туди не дістає.
4. Згенеруй пароль БД так, щоб він не потрапив ні в state, ні в plan; збережи його в Key Vault.
5. Перевір: `terraform state pull | grep -i password` не знаходить нічого.
6. Імпортуй один ресурс, створений руками, і доведи планом, що він тепер під контролем коду.
7. Перейменуй ресурс у коді і використай `moved`, щоб не перестворювати його.

## Критерії прийому
- [ ] Remote state із блокуванням; паралельний apply блокується
- [ ] Пароль БД відсутній у state і plan
- [ ] Ресурс, створений руками, імпортований
- [ ] Перейменування зроблене через `moved` без перестворення

## Пастки
- Plan-файл, збережений як артефакт пайплайну, теж містить чутливі дані.
- `state rm` без розуміння лишає ресурс у хмарі без керування і без обліку.
- Один спільний state на всі середовища означає, що помилка в dev може зачепити prod.
