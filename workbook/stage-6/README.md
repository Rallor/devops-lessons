# Етап 6. Кілька сервісів і команд → платформа (тижні 24–27)

## Тригер
Зʼявилися сервіси нотифікацій, платежів і звітів; три команди, кожна хоче деплоїти сама. Кожен новий сервіс — новий план App Service, нові модулі й копія пайплайну. Удень ресурсів бракує, вночі 80% простоює. Воркер звітів треба масштабувати за чергою, а не за CPU.

## Вимоги етапу
1. Нова команда виводить сервіс у staging за шаблоном без участі DevOps за ≤1 день.
2. Деплой лише через GitOps; прямий `kubectl apply` у prod заборонений RBAC; ручні зміни відкочуються самі.
3. Кожен workload: requests/limits, readiness і liveness (startup де треба), non-root, PDB.
4. API масштабується HPA, воркер — за довжиною черги.
5. Секрети з Key Vault через Workload Identity; у git немає Secret-маніфестів із даними.
6. NetworkPolicy default-deny між namespace.
7. Canary або blue-green з автоматичним відкатом; rollback через `git revert`.
8. Вбивство пода, drain ноди і рестарт воркера не порушують SLO з Етапу 5.
9. Вхідний трафік через Gateway API; ingress-nginx відсутній.
10. Кластер у Terraform; вартість по namespace видима.

## ADR етапу
- **ADR-019.** Чи потрібен Kubernetes: AKS, AKS Automatic, Container Apps чи лишитися на App Service — за цифрами з тригера.
- **ADR-020.** ArgoCD проти Flux; структура GitOps-репозиторію.
- **ADR-021.** Реалізація Gateway API; чи потрібен service mesh.
- **ADR-022.** Секрети: CSI Driver проти External Secrets Operator; критерій здоровʼя проєкту.
- **ADR-023.** Прогресивна доставка: Argo Rollouts, Flagger чи ручний canary.

## Ворота етапу
Хтось сторонній виводить сервіс за твоїм онбординг-документом; `kubectl delete pod` і drain ноди під навантаженням не ламають SLO; ручна зміна в prod відкочується ArgoCD; canary з деградованою версією відкочується сам.
