# Блок 6.7 — Безпека кластера

**Час:** ~5 год · **Передумови:** 6.6

## Навіщо це зараз
Кілька команд в одному кластері означають, що сусід може стати твоєю проблемою. Ізоляція має бути технічною, а не на довірі.

## Теорія
- Pod Security Standards (restricted), securityContext, `readOnlyRootFilesystem`.
- User Namespaces: root у контейнері без root на вузлі.
- NetworkPolicy: default-deny і явні дозволи.
- Обмеження дозволених реєстрів і перевірка підписів образів на admission.
- ValidatingAdmissionPolicy і MutatingAdmissionPolicy на CEL як вбудована альтернатива вебхукам; Kyverno і Gatekeeper.

## Завдання
1. Увімкни PSS restricted для namespace застосунків; полагодь усе, що перестане стартувати.
2. Постав NetworkPolicy default-deny і відкрий лише потрібні напрямки; перевір, що под із чужого namespace не достукається.
3. Заборони образи з невідомих реєстрів через політику; перевір негативно.
4. Додай перевірку підпису образу (з блока 3.3) на admission: непідписаний образ не запускається.
5. Напиши одну політику на CEL (наприклад, обовʼязкові requests) і одну аналогічну в Kyverno; порівняй у нотатках.
6. Проскануй кластер інструментом на кшталт kube-bench або trivy k8s і розбери знахідки.
7. Опиши в `docs/notes/cluster-security.md` модель загроз: від чого ти захистився, а від чого ні.

## Критерії прийому
- [ ] PSS restricted діє; workload відповідають
- [ ] NetworkPolicy default-deny; крос-namespace доступ закритий
- [ ] Непідписаний образ не запускається
- [ ] Модель загроз описана чесно, включно з тим, що лишилось відкритим

## Пастки
- NetworkPolicy без egress-правил ламає DNS: под перестає резолвити імена.
- `readOnlyRootFilesystem` без emptyDir для тимчасових файлів валить застосунок.
- Політика, яка застосовується лише до нових подів, лишає старі як були.
