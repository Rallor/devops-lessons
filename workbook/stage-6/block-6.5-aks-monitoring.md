# Блок 6.5 — AKS і моніторинг кластера

**Час:** ~6 год · **Передумови:** 6.4, Етап 4

## Навіщо це зараз
Локальний `kind` не має ні мережі хмари, ні ідентичностей, ні рахунку в кінці місяця. Кластер має зʼявитися як код, а не з порталу.

## Теорія
- AKS через Terraform: node pools, мережа (Azure CNI Overlay), managed identity, інтеграція з ACR і Key Vault.
- Оновлення версій кластера й нод, maintenance windows.
- Node Auto Provisioning проти cluster autoscaler; spot-пули для non-prod.
- kube-prometheus-stack, ServiceMonitor і PodMonitor, kube-state-metrics — продовження Етапу 5.
- Вартість по namespace.

## Завдання
1. Опиши AKS у Terraform: system і user node pool, overlay-мережа, інтеграція з ACR і Key Vault.
2. Підніми кластер, розгорни туди застосунок з Helm chart блока 6.3.
3. Розгорни kube-prometheus-stack; підключи ServiceMonitor для своїх сервісів.
4. Перенеси SLO-дашборди з Етапу 5 у кластерну інсталяцію; переконайся, що метрики збігаються.
5. Проведи оновлення версії кластера з увімкненим PDB і покажи, що сервіс вижив.
6. Увімкни spot-пул для non-prod і покажи економію в Cost Analysis.
7. Розрахуй вартість кластера на місяць і порівняй з App Service із Етапу 4; допиши цифри в ADR-019.

## Критерії прийому
- [ ] Кластер піднімається з коду; ручних кроків у порталі немає
- [ ] Метрики збираються, SLO-дашборди працюють
- [ ] Оновлення кластера пройдене без порушення SLO
- [ ] Вартість пораховано і додано в ADR-019

## Пастки
- Node pool без запасу по IP у підмережі: кластер не зможе масштабуватись.
- Spot-вузли в prod дають несподівані виселення.
- kube-prometheus-stack за замовчуванням збирає багато: перевір обсяг і вартість зберігання.
