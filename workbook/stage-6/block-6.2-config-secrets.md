# Блок 6.2 — Конфігурація і секрети

**Час:** ~4 год · **Передумови:** 6.1

## Навіщо це зараз
Секрети в git у base64 — це той самий секрет у git. На Етапі 4 ти вже поклав їх у Key Vault; тепер кластер має брати їх звідти.

## Теорія
- ConfigMap проти Secret; base64 — це не шифрування.
- Монтування як env проти volume: чому volume оновлюється без рестарту, а env ні.
- Workload Identity (не застаріла Pod Identity); Secrets Store CSI Driver і External Secrets Operator.
- Здоровʼя проєкту як критерій вибору залежності.

## Завдання
1. Винеси всю нечутливу конфігурацію в ConfigMap; перевір, що зміна підхоплюється як очікується.
2. Налаштуй Workload Identity: service account пода отримує доступ до Key Vault без секретів у кластері.
3. Підключи CSI Driver або ESO за ADR-022; секрет зʼявляється в поді з Key Vault.
4. Переконайся, що в git немає жодного Secret-маніфесту зі значеннями.
5. Зроби ротацію секрету в Key Vault і перевір, скільки часу займає його поява в поді.
6. Перевір негативно: под без правильної анотації service account не отримує секрет.
7. Опиши в нотатках, що буде, якщо Key Vault недоступний у момент старту пода.

## Критерії прийому
- [ ] Секрети приходять із Key Vault; у git їх немає
- [ ] Workload Identity працює без збережених облікових даних
- [ ] Ротація перевірена, час підхоплення заміряний
- [ ] Поведінка при недоступності Key Vault описана

## Пастки
- Секрет, змонтований як env, не оновиться до рестарту пода.
- Неправильний audience або federated credential дає помилку, яку легко прийняти за проблему мережі.
- ESO і CSI Driver вирішують схожі задачі по-різному: змішувати обидва в одному кластері без причини — зайва складність.
