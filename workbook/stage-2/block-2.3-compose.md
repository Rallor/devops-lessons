# Блок 2.3 — Compose і мережі контейнерів

**Час:** ~5 год · **Передумови:** 2.2

## Навіщо це зараз
Розробник має піднімати весь стек однією командою. Заразом тут зʼясовується, що опублікований порт контейнера дивиться в інтернет повз твій firewall із Етапу 1.

## Теорія
- `services`, `networks`, `volumes`; DNS за іменем сервісу в bridge-мережі.
- Named volumes проти bind mounts; де зберігаються дані.
- `depends_on` з `condition: service_healthy`; чому просто `depends_on` нічого не гарантує.
- `.env`, override-файли для dev і prod, profiles.
- Docker і NAT: публікація порту через DNAT, MASQUERADE для вихідного трафіку, ланцюг `DOCKER-USER`.
- Docker Engine 29: експериментальний nftables-бекенд.

## Завдання
1. Опиши в compose повний стек: API, воркер, фронт, Postgres, Redis.
2. Додай healthcheck кожному сервісу; зроби залежність API від готовності БД, а не від її запуску.
3. Налаштуй named volume для даних БД і seed-дані для dev.
4. Зроби два override-файли: dev (з hot reload і відкритими портами локально) і prod-подібний.
5. Додай ліміти CPU і памʼяті кожному сервісу.
6. Опублікуй порт Postgres як `5432:5432`, переконайся ззовні, що він відкритий попри `ufw deny`, і поясни в нотатках чому.
7. Полагодь це двома способами: публікація на `127.0.0.1` і правило в `DOCKER-USER`. Опиши різницю.
8. Перевір, що `docker compose up` на чистій машині дає робочий стек без ручних кроків.

## Критерії прийому
- [ ] Один `docker compose up` піднімає стек із тестовими даними
- [ ] Усі сервіси мають healthcheck і ліміти
- [ ] БД і Redis недоступні ззовні; перевірено `nmap` з іншої машини
- [ ] У нотатках пояснено, чому Docker обходить `ufw`

## Пастки
- `depends_on` без `condition` стартує API раніше, ніж БД готова приймати зʼєднання.
- Bind mount поверх каталогу з даними в образі ховає його вміст.
- Volume з даними БД, створений від root, потім не доступний non-root користувачу контейнера.
- `docker compose down -v` знищує дані разом із volume.

## Підказки
<details><summary>Підказка 1</summary>
`iptables -t nat -L DOCKER -n` покаже DNAT-правила, які створює Docker. Твої правила `ufw` живуть в іншому ланцюгу і не перевіряються для forwarded-трафіку.
</details>
<details><summary>Підказка 2</summary>
Публікація `127.0.0.1:5432:5432` прибирає порт з інтернету, але лишає доступ через SSH-тунель з блока 1.4.
</details>
